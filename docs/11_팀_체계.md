# 팀 체계 (오너 결정 2026-10-15)

> 직원들이 단계마다 일을 넘기기만 하고 결과를 책임지는 사람이 없어서, **팀 단위로 묶고 팀마다 Opus 5.5 팀장**을 둔다.
> 팀원(실무)은 Sonnet 5.5, 팀장과 CEO 는 Opus 5.5. 이 문서는 `docs/10_조직도_Org.md` 보다 우선한다.

## 조직도

```
오너 (사람) ── 승인·게시·정산
   │
  CEO (Opus) ── 배치 목표, 팀 간 조율, 최종 출고 판정(SHIP/HOLD)
   │
   ├─ 기획팀      pm-lead      (Opus)  ← researcher-*, pm-*        (Sonnet)
   ├─ 제작팀      maker-lead   (Opus)  ← designer-*, maker-*       (Sonnet)
   ├─ 품질팀      qa-lead      (Opus)  ← qa-*                      (Sonnet)
   └─ 사업운영팀  marketer-lead (Opus) ← marketer-*, cfo-*         (Sonnet)
```

## 직원 ID 와 오피스 위치
| ID | 직함 | 모델 | 오피스 방 (ID 앞부분으로 결정) |
|---|---|---|---|
| `ceo` | CEO | Opus | 대표실 |
| `pm-lead` | 기획팀장 | Opus | 기획·디자인 |
| `maker-lead` | 제작팀장 | Opus | 제작 |
| `qa-lead` | 품질팀장 | Opus | 검수 |
| `marketer-lead` | 사업운영팀장 | Opus | 마케팅 |
| `researcher-N`, `pm-N`, `designer-N`, `maker-N`, `qa-N`, `marketer-N`, `cfo-N` | 팀원 | Sonnet | 각 부서 |

팀장 역할 정의: `.claude/agents/<팀장 ID>.md` (예: `.claude/agents/pm-lead.md`). 팀원은 기존 `.claude/agents/<역할>.md`.

## 결재 관문 (생산 라인 순서)
| 관문 | 누가 | 무엇을 | 통과 못 하면 |
|---|---|---|---|
| G0 킥오프 | CEO + 기획팀장 | 배치 목표, 상품별 지시, 우선순위 | 상품 제외 |
| G1 사양 승인 | 기획팀장 | `spec.md` 가 수요 근거·완성 기준·검수 체크리스트를 갖췄는지 | 기획자가 1회 수정 → 그래도 안 되면 팀장이 직접 고쳐 확정 |
| G2 제작 승인 | 제작팀장 | 산출물을 직접 열어/실행해 사양·디자인과 맞는지 | 제작자 1회 수정 → 남은 작은 문제는 팀장이 직접 수정 |
| G3 품질 판정 | 품질팀장 | 검수자 보고를 종합해 최종 PASS/FAIL (팀원 판정은 의견) | 제작자 수정 → 재검수 → 재판정 (최대 2회) |
| G4 판매 승인 | 사업운영팀장 | `listing.md` 와 `compliance.md` 가 규정·정직성 기준을 지키는지 | 마케터·재무 1회 수정 → 팀장 확정 |
| G5 출고 판정 | CEO | SHIP/HOLD, `READY_FOR_OWNER.md`, 승인 요청 | HOLD + 후속 과제 |

## 원칙
- **팀장은 일을 대신하지 않는다.** 지시하고, 검토하고, 결정한다. 직접 고치는 것은 1회 수정 후 남은 작은 문제에 한한다.
- **판정은 팀장이 책임진다.** 팀원 판정은 근거 자료이고, 관문 통과 여부는 팀장 결정이다. 결정 이유를 파일에 남긴다(`spec.md` 끝 `## 기획팀장 승인`, `build_notes.md` 끝 `## 제작팀장 승인`, `qa_report.md` 끝 `## 품질팀장 판정`, `compliance.md` 끝 `## 사업운영팀장 승인`).
- **팀 간 충돌**(예: 기획 범위 vs 제작 가능성)은 CEO 가 결정한다.
- 절대 규칙(CLAUDE.md)은 직급과 상관없이 같다. 팀장도 계정·결제·게시·발송·승인을 하지 않는다.
- 비용: Opus 호출은 관문당 1회가 기본. 반복이 필요한 건 팀원(Sonnet)이 한다.
